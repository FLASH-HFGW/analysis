## Status semantics and late Rucio recovery

`rucio_status=0` is the logbook release signal for raw input.
`reco_done` describes the reconstruction row. Canonical publication
verification requires ROOT integrity and receipt checks, and a
separate guarded write reconciles version, output path and counter
in the logbook. An occupied attempt or a submitted job is separate
from verified publication, and verified publication is separate from
the logbook update.

The original eligibility rule required both `rucio_status == 0` and
`reco_done == 0`. Comparing the 25 and 26 November logbook snapshots
identified 23 in-scope rows for which Rucio changed from 2 or 4 to 0
while `reco_done` remained `-1`. The 23 canonical raw files were
nonempty, and the rows had empty reconstruction metadata and no
ROOT products or attempt histories at the audit. This establishes
the observed use of `-1` for that unreleased-input cohort. The
original service that writes the sentinel remains unidentified.

The enabled ROOT-only opt-in `late_rucio_recovery` admits this exact
status combination when the canonical raw exists, reconstruction
version/path are blank and the requested version is blank or 3.1.
An existing ROOT object blocks duplicate submission. Active-attempt,
retention and retry rules remain in force. The recovery marker in job
state allows the guarded success update from `-1` to `1` after a
validated ROOT receipt. Other negative states do not become eligible.
The official preview found 23 candidates and planned 20 admissions.

The identified runs are 1220, 1262, 1264, 2040, 2041, 2195–2208,
2269, 2271, 2272 and 2380. During integration, 20 had validated
archive products and persisted `sheet_updated` status. Runs 2272
and 2380 were submitted as clusters 6073 and 6074. Both were later
observed with Condor status Completed in the same bounded check;
ROOT verification and logbook reconciliation were still pending.
Run 1220 is recorded as `submitting`, with no ClusterId and no
matching queue or history record for its exact persisted attempt.
It needs operator review before any retry or state repair.

## Authentication and Discord

On 26 November, the original Run 1220 submit returned exit code 1.
Its restricted local diagnostic contains an approval-shaped link
that the deployed parser does not accept. The exact cause and prompt
wording must be checked locally before changing detection or treating
the attempt as safe to retry. Later accepted submissions, including
6073 and 6074, demonstrate scheduler submission worked again; the
Tier-1 OAuth credential query separately reported a valid credential.
No new submit was issued to probe authentication during consolidation.

When Condor explicitly requests interactive approval, an authorized
operator should open the exact HTTPS link generated by Condor and
approve the request. The accepted origin is
`condor.psge.cloud.infn.it` with an approval path under `/key/`.
Never invent URLs, and never record an approval link in Git or in a
shared report. Check the exact attempt in queue and history before
considering any further submission. Recovery requires a confirmed
accepted submission. Approval or an otherwise successful cron cycle
alone does not demonstrate that submission recovered.

`autoreco/notify.py` reads the private host webhook at send time.
It alerts for recognized Condor authentication failures, other submit
failures, HOLD, repeated or exhausted reconstruction failures, ROOT
publication or integrity problems, persistent logbook failures and
scheduler exceptions. The controlled HTTPS delivery test returned
HTTP 204. Routine reconstruction success and normal cron cycles do
not generate alerts. Recovery notifications require evidence such as
an accepted submission, leaving HOLD, a validated publication or a
successful logbook update. Generic scheduler faults do not get an
automatic recovery message merely because a later cycle completes.

Deduplication state is `discord-notifications.json` under the Run3
runtime. It is atomically replaced under the production lock and
separate from scientific state. Reminders default to disabled.
Notification errors leave the original scheduler behavior intact.
The persisted sent markers for exhausted runs 2522, 2524 and 2536
were retained across consolidation. Each has two failed attempts
and remains blocked. Do not clear its alert marker or retry history.

and the [documentation policy](../DOCUMENTATION_POLICY.md). Verify
current Git ancestry, worktree changes, active cron, configured limits

diagnostic. Validate changes in isolation and use the official dry
run before allowing the existing cron to act.
